# MVP 与产品取舍

第一版的上线标准不是「功能齐了」，而是「能开始向客户学习了」：开发和测试阶段几乎学不到与客户有关的东西，所以第一版要缩到只兑现对客户的核心承诺。上线后同理：新功能默认不加，要加就排队、当实验验证。判断对没对上市场，先看留住了多少人、用户没了它有多沮丧，而不是收入。上线前怎么验证需求，见〈方向与需求验证〉。

## 速览

- **最关键的问题**：我们对客户承诺的核心是什么，这个功能在兑现它，还是我改演示时顺手加的？我想做它，是出于对用户的了解，还是只因为同行有、有人说好？我的产品是一次性价值，还是要被反复使用，有没有人在付钱却不用？
- **首选打法**：
  - **把第一版缩到能开始学习**：每个功能标成必须有、可以有、不需要，确有必要才进第一版；缩小不是做简陋，仍要兑现对客户的核心承诺。
  - **上线后默认不加，要加就排队验证**：请求先分诊，追问客户为什么要而不是照他给的办法做，值得做的当实验，在建数设上限。
  - **判断对上了没有**：先分一次性价值还是反复使用，看激活率或留客率，再问用户「没了它会有多沮丧」；别只看收入，它只是初级验证。
- **最常见的坑**：觉得第一版要做完整再拿出去，或把演示越改越完整；把缩小做成简陋；只看收入，没有早期吸引力就扩张。
- **证据**：全是各自提出者的个人经验和单个案例，没有对照，也没有第三方复现；卡里的数字线多为口头估算、转引的外部说法或提出者自己的换算。
- **不在这张卡里**：砍到多少算够、第一版多久上线（来源只有判据，没有天数或功能个数）；什么时候止损或转型。

## 先问这几个问题

1. 我们对客户承诺的核心是什么？这个功能是在兑现它，还是我改演示时顺手加的？
2. 用户提的这个大方案，背后是哪一个具体时刻的需要？只满足那一刻，窄方案长什么样？
3. 我是不是只在琢磨怎么把某个部件做得更好，却没问过为什么一定要有它？
4. 我想做它，是出于对用户的了解，还是只因为同行有、有人说好？
5. 现有功能认真测过、问题都解决了吗？加这个的成本算过吗？
6. 我的产品是一次性价值，还是要被反复使用？有没有人在付钱却不用？

## 打法

### 1. 把第一版缩到能开始学习为止

写代码、做测试的那段时间里，你对客户几乎什么都学不到；真正的客户学习要等产品交到他们手上才开始，发布拖得越久，学习就开始得越晚。研发和测试本身省不掉，能压缩的是从定下需求到交付使用之间的时长。缩小不是做简陋，仍要兑现对客户的核心承诺。
另有一条独立的理由：复杂系统要从一个能跑的简单系统长出来，因为各部分要在运行中靠时间互相检验。做法相同，理由不同。
1. 从零开始，把每个功能过一遍，确有必要才放进第一版，并且从能解决客户头号问题的功能开始。
2. 给演示里的每个功能标三类之一：必须有、可以有、不需要。不需要的扔掉，可以有的放进备选列表，和必须有的功能有依存关系的另当别论；再对第二、三大问题重复一遍。
3. 客户提的要求（比如和他们在用的其他软件对接），研究后按重要程度决定加不加。
4. 发布时讲明要收费，但月末再结账，免费试用期之外不当场要信用卡，不急着备好多套餐；不去优化服务器、代码和数据库，目标是学习，不是优化。
- 做到什么程度算完成：每个功能都有标签，备选列表里收着可有可无的，发布前的待办里没有性能优化（判断）。
- 最容易往第一版里加东西的，是刚做完方案访谈、觉得客户反应不错的时候；标签依据的是客户在访谈里的反应，样本小、客户又爱客套时，容易把嘴上要的标成必须有（以上两点都是判断）。

### 2. 把大方案还原成某个时刻的需要

用户提出的有时是一个大方案（这一做法是对来源里三个例子的概括，不是提出者的原话）。还原成某个时刻的需要，只做那一点，被砍的部分降成窄方案或不显眼的入口，而不是整个删掉。
1. 问：这个大方案背后，是哪一个具体时刻的需要？
2. 问：只满足那一刻会是个什么窄方案，有没有必要做成解决所有问题的完整方案？
3. 被砍掉的部分，能不能降成一个隐蔽入口？
4. 再问一句「为什么一定要有它」，别只问怎么把它做得更好。这一问问的是该不该存在，上面几问问的是只服务哪个时刻。
- 先弄清自己砍的理由：来源的三个例子里，有的是为了安全，有的是为了守住「能立刻找到对方」的体验，并不都是范围。

### 3. 上线后：默认不加，要加就排队验证

人们的通常反应是把产品做大做全，往往适得其反：多余功能稀释核心承诺；第一版只验证了框架，现有功能还没验透；每个功能都有成本；你还不知道客户到底想要什么，所以新功能要当作实验来看。
至于姿态，对新点子默认说不，让提议的人来举证（判断）；用户的反馈只能帮你了解他们的想法，别直接当功能清单。
1. 请求进来先和当前最要紧的事比：是不是恰当时间的恰当请求（比如注册流程有严重问题时，其他步骤的请求先放一放）。
2. 分类：小功能、修 bug，还是值得专门告诉客户的功能；小而必须马上办的立刻做，其余按优先级排队。
3. 排队的先问「值得解决吗」，找不到充分理由就毙掉；客户的请求，打电话或见面追问他为什么要，找到问题根源，而不是照他给的办法做。
4. 给同时在建的功能设上限，起步按联合创始人或团队人数来。
5. 值得做的，先做产品模型给客户看，客户非常满意再编码；先部分部署给少数客户做易用性测试；全面部署后对比前后一周的转换率。
- 做到什么程度算完成：每条请求都有去向，在建数不超上限；上线后大部分时间花在评估和改进现有功能上。
- 只有一两个人的早期团队，可以先只取请求分诊和在建上限两点（判断，来源没这样说）。

### 4. 判断对上了没有：先看留住多少，再问没了会不会沮丧

收入只是初级验证：很多客户在付钱却没在用，有的是公司替他付，有的是忘了停自动扣费。
1. 先分类型：一次性价值的产品（婚礼摄影、书）看激活率，反复使用的产品（软件服务、社交、餐厅）看留客率。
2. 每周固定时间看转换率，找流失最大的一步；给待做功能排序；大胆提假设但只用最简版本验证；没效果的功能重做或删掉。
3. 盯住留客人数。提出者的标准是月复一月留住约四成已激活用户。
4. 到了这条线，再问用户一道题：如果以后不能再用这个产品，你会有多沮丧？选项为非常沮丧、有点沮丧、没关系、已经不用了。选最强烈的非常沮丧一档的超过四成，很可能说明它属于必须有。这道题只判定有没有早期吸引力，不教你怎么得到；样本要足够，面对企业客户别直接这样问，可能引起反感。
5. 没有早期吸引力就别急着扩张；有了之后，立刻把重心转到公司能持续发展上。
6. 另一类信号是口碑：看用户在公开场合怎么形容你。提出者认为用好玩、爽来形容的产品能自己传开，用省钱、好用的工具来形容的未必；新产品放出去后公开平台上没人自发说好玩，就当它传播不起来。这测的是愿不愿替你说话，上面几步测的是离不离得开。

### 5. 平台和网络效应类产品：先在小圈子里证明价值

这两类产品的流程也能用，但起步要调整：先在小范围里证明价值，别急着铺开。
1. 网络效应类：第一个里程碑是做出人们想要的产品，用反复使用率和投入程度衡量；小规模验证后再靠传播冲向引爆点，引爆点之前要先找到生存之道。
2. 交易市场类：买家和卖家各做一张商业假设图、各自访谈；先找一个已经存在、双方交易热情和麻烦程度都高的小圈子做原型，别一上来做新的大市场。
3. 不要用自动方式撮合买卖双方，先由人手工撮合，同时学哪些环节适合自动化。

## 常见的坑

- 觉得第一版要做完整、做扎实再拿出去；或在方案访谈里把演示越改越完整，没意义的功能混进第一版。
- 把缩小做成简陋：激活流程没兑现着陆页上的承诺，第一印象只有一次。
- 同时在建太多；只照客户给的办法做；把完成定义成写完代码（判断）。
- 只看收入，或为了创收选错办法（把授权做成一次买断、接定制开发）；没有早期吸引力就扩张。
- 把默认否定当教条：提出者自己也承认优先级的判断很凭感觉，它不是可复核的流程。

## 两派看法

**新功能的需求从哪来。** 一派：不靠调研、分析、讨论和竞品，只来自对用户的了解和自己的需求；调研对细节改进有用，对决定新功能没意义。另一派：创始人做不成客观的客户，「我自己会用」替代不了访谈，要写会被推翻的假设、逐场访谈。两边在「别去问用户要什么功能」上其实一致。
怎么选（判断，依据两边各自的前提）：前一派的前提是做的人本身就是典型用户、长期观察用户、产品是用户说不出口的新品类；创始人不是目标用户，或没有这种积累，就走访谈。后一派的提出者自己的经历也提醒：发现目标用户越来越像自己、对客户的问题失去热情，是危险信号。

**注册和收费的摩擦。** 一派：发布时减小注册阻力、推迟收费、月末结账。另一派：验证付费意愿时别让注册太容易，要书面或预付承诺。提出者自己的折中是减小阻力，但不能影响学习。
怎么选（判断）：前者针对发布时的摩擦，后者针对做第一版之前验证付费承诺。提出者还建议第一天就收费，合起来读大概是第一天讲明收费、推迟结账，这是推断。

**上线后是改进现有，还是探索新的。** 一派：把大部分时间用来改进现有功能。另一派：把单一目标做到极致，会吃掉探索的预算。怎么选（判断）：并不真冲突，现有功能只验证过框架，改进它本身就是探索，同时新功能仍要当实验；两边的话别混着引。

**自报的态度，还是实际的行为。** 那道沮丧题是用户自报，而客户可能说假话；提出者的衔接办法，是同时看留客率这类行为数据。

## 什么时候这套不管用

- 默认否定、只做主场景，出自用户基数很大、已经领先的团队；追赶者面对「同类都有、客户明确因此流失」的功能怎么办，来源没处理。为一小部分人把入口藏起来，用户还不多时，那一小部分人可能就是全部早期用户（判断）。
- 好玩这个检验出自大众社交类产品；企业工具的口碑常在私下渠道，公开平台没声音不等于没人用（判断）。
- 例子和工具都是软件。产品一旦发布就难以收回的（受监管的、硬件的、一次性交付的），尽早发布的代价不同（判断）。
- 已有成熟做法可以直接复用时，不必从简单版慢慢长；什么算简单、什么算能运转，来源也没给判据（判断）。
- 四成这条线对一次性价值的产品含义未必一样；样本很小时更像方向而不是判决；一周只有几十个用户时，周转换率的波动可能大过信号（判断）。

## 例子

- 一款大众通信产品的三次取舍：用户想把数据存在云端，只做了换手机时的数据迁移；用户嫌手机上打字辛苦，没做完整的电脑版（会让人不再信对方能立刻收到消息），而是做成只借电脑键盘来输入的辅助，后来才补了带界面的网页版；动态里只能发照片，发纯文字的入口放在隐蔽的地方。来源只写了做法与理由，没写效果。
- 一位创业者的消费类产品，不少妈妈注册、付费、夸奖，推向更大人群却推不动：目标用户太忙，难以关注产品，早期访谈时她们就总临时取消、改约，当时没被重视。他最后发现公司越来越技术导向、目标用户越来越像自己，对客户的问题失去了热情，把公司卖给了第一位客户。这全是他事后的自述；退出的主因是创始人自己的状态，不能直接读成「产品没对上市场」。

## 证据有多硬

- 这些来源全是各自提出者的个人经验和单个案例，没有对照，也没有第三方复现；其中一个来源是一位成功产品负责人的事后口述，一些数字据上下文还原。
- 四成这条线，来源只给了结论和一句附带说明，谁做的对比、样本构成都没交代；月复一月留住四成已激活用户，是提出者自己的换算。
- 「绝大多数新点子该否」「以前的功能大半可砍」是口头估算；在建上限等于联合创始人数，依据只是引用了一个讲开发流程的外部说法。
- 好玩这个检验是提出者的经验判断，没有量化口径；他拿付费和省钱做的对比用的是假设语气，不是实验。提出者说产品并非为了交友，可他讲的安装故事里，拉动安装的也许恰是交友好奇，动机陈述是事后自述（判断）。
- 平台类的例子，以及「为什么一定要有它」这一问的例子，都是成功的案例，没有同样做法却失败的对照。
- 有一种相反主张，认为该先想清逻辑再动手、反对边做边试；但它的主要论据被查出有史实错误，已被搁置，不构成对「先小步做出来」的反驳（判断）。

## 一页清单

- [ ] 能一句话说出对客户的核心承诺，进第一版的每个功能都在兑现它
- [ ] 演示里的功能都标了必须有、可以有、不需要，备选列表里有存档
- [ ] 每个大请求都写出了「只服务哪一个时刻」
- [ ] 请求先分诊，被毙的有理由，客户的请求追问过根源，在建数有上限
- [ ] 知道自己是一次性价值还是反复使用，盯对了指标，查过有没有人付钱不用
- [ ] 没有早期吸引力之前不扩张

## 这张卡没覆盖的

- 砍到多少算够：来源只有判据，没有天数或功能个数，第一版多久上线给不出
- 什么时候止损或转型：留客低于四成多久算对不上、几轮迭代后该转
- 硬件、服务、大额企业订单类产品的第一版怎么做
- 低频或一次性价值产品的匹配指标门槛；早期用户很少时怎么读那道题和留客率
- 付费大客户强要求某个功能（不做就不签）怎么办；竞品上了某个功能要不要跟
- 团队内部在功能上分歧时谁拍板
- 收费时机与定价，见〈定价〉；匹配之后的扩张节奏、何时招人
